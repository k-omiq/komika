Two decisions that gate everything

Before the phase plan — two realities that are bigger than any single feature. Both deserve a conscious call now, because they shape the architecture and the business.

Largely defused · native-first

A static SPA can't be found

Update: going native-first (Desktop + iOS/Android, no public web app) removes this as a launch gate — native apps are distributed via stores / direct download, not crawled. The options below only matter if a web build or marketing/landing site is added later. Kept for reference.

The app is adapter-static with ssr = false. That's excellent for security and cost — but crawlers and social scrapers get an empty HTML shell. For a catalog whose growth depends on ranking for "read <title> online" and on rich link previews, this is the single biggest threat to the business model. Google can render JS slowly and unreliably; Bing, Discord/Twitter/Facebook preview bots, and most others cannot.

  • ABuild-time prerender (SvelteKit prerender + entries()). Fine for a bounded set; unworkable alone for a large, constantly-updating catalog.
  • BEdge SSR for public routes only — server-render home / browse / genre / series (content + meta + JSON-LD) at the edge, keep the app a SPA for the reader and account flows.
  • CDynamic rendering (serve prerendered HTML to bots by user-agent). Tolerated, but a maintenance anti-pattern. Last resort.
Recommendation → B. SSR the public catalog at the edge; keep the app shell static. This partially reverses the earlier "no SSR anywhere" call — but only for anonymous public pages, so the static app keeps its hardened surface. It stays not Next.js (SvelteKit with an edge adapter). Needs a decision from you, because it changes the deploy topology.
Critical · Legal & distribution

Aggregating manga is fine privately — a public, monetized, SEO-promoted service is a different risk class

Komika serves copyrighted manga via Tachiyomi-style sources (the Mihon/Suwayomi ecosystem). Self-hosted, that's a personal tool. Public + indexed + paid changes the exposure materially:

  • 01Takedowns. SEO visibility makes you a target; you'll need a DMCA agent and a real takedown workflow.
  • 02App stores. Apple and Google routinely reject piracy-reader apps — Tauri mobile won't change that verdict. Plan desktop + installable PWA; treat store apps as high-risk.
  • 03Donations. Donation-only (no paywalls, no ads) is a softer, non-commercial posture — but processors can still refuse accounts tied to infringing content, so the donate flow needs one that tolerates the category, plus clear terms.
  • 04Hosting & ads. Some hosts and ad/analytics networks decline this category.

Not legal advice, and not a judgment on the model — you decide it. But "production readiness" here is as much legal/ops as engineering. Licensed/original content, or shipping as a self-host distribution, changes this calculus entirely. Get counsel before a public, monetized launch.

The build, phase by phase

Ordered by dependency. The first two phases — the unified backend / accounts / social, and the admin console — are shipped. What remains is the update engine, the image + growth layer, hardening, and launch. Effort assumes one focused engineer; a small team compresses this. Later phases overlap rather than following strictly.

✓

Unified backend · accounts · real social

Shipped

The Komika server implements komika.graphql — federating Suwayomi for catalog/chapters/pages/library/progress, and adding what Suwayomi lacks: accounts, and real multi-user reviews / ratings / comments.

  • Stack chosen — Rust (Axum + async-graphql + SQLite), coherent with the Tauri core and the low-resource / secure goals.
  • Accounts & auth — register / login, argon2 hashing, bearer-token sessions; login/register UI + auth store wired through the client.
  • Social API — per-series reviews (1–10) aggregated into ratings, per-chapter comment threads, spoiler tags.
  • Client cut over — the social.ts localStorage store swapped for backend.* (auth-gated, with a local fallback for offline / mock).
  • Library + progress — mark and setProgress persist through the backend.
Exit multi-user ratings/comments persist server-side; sign-in works; catalog served through the unified API. Verified live.
✓

Admin "manga DB" console

Shipped

The operator surface for the catalog — a separate, admin-gated SPA against the unified server.

  • Admin-gated console — isAdmin login; catalog table (library / search) with cover, status, chapter count, scan cadence.
  • Per-series editor — scan-interval override, poll cadence, force pause, and status flags (completed / hiatus / …).
  • Persisted + folded in — overrides stored server-side and folded into every Series.status / scan, so the reader sees them too.
Exit operators manage scan policy + status flags; overrides propagate to the reader. Verified live.
✓

Adaptive scan scheduler

Shipped

The update engine that keeps the catalog fresh — a background scheduler driven by each series' ScanPolicy.

  • Scheduler — a background task computes each series' rolling average time-between-chapters, resolves the effective interval (admin override → avg), skips paused/completed/hiatus, and re-fetches overdue series from Suwayomi; detects new chapters; persists scan state (series_scan_state), folded back into Series.scan.
  • Health — a scanStatus query (library size, overdue count, last tick, next due). Verified live against Suwayomi.
  • Remaining: new-chapter notifications (web push + native), and wiring the scheduler to drive the image cache-fill.
Exit the scanner runs on schedule and keeps the catalog current. Verified live.
4

Image pipeline · Cloudflare Worker + B2

Built · needs infra
code done

Mostly a web concern — deprioritized native-first. Native (Tauri) apps fetch image bytes directly from the source via the Rust fetch_image core (setting the right headers), so they never need the CORS-bypassing Worker at all. The Worker + client seam stay code-complete for an optional web build. B2 is now used first for backup (Litestream). Server-side, image URLs still resolve through Suwayomi; a CDN cache in front is a scaling nicety, not a blocker.

  • Worker (apps/worker) — proxy with edge cache (Cache API), hotlink protection + source-host allowlist, permissive CORS, long immutable cache headers, streamed bodies. Done.
  • B2 read/write-through — S3-compatible (SigV4); read-through, and write-through on a &cache=1 hint (for popular/marked). Fully optional + fails open to plain proxy. Done.
  • Client seam — ImageProvider proxy mode points at the Worker (/img?src=…); native keeps direct fetch. Done.
  • Remaining: stand up Cloudflare + B2, wire the scanner-driven cache-fill, add cost controls (TTLs, egress budgets, monitoring).
Exit covers/pages served via CDN with real caching; hot content in B2; long tail proxied on demand.
5

SEO & discoverability

Deprioritized · native-first
later / if web

Deprioritized: with no public web app, there's nothing for crawlers to index — discovery comes from the app stores / direct distribution, not SEO. This whole phase only returns if a web build or marketing site is added. The tasks below are kept for that scenario.

  • Edge SSR for public routes — server-render home / browse / genre / series with content in the HTML.
  • Clean, canonical URLs — switch routing from opaque ids to slugs (/series/solo-leveling), 301 old → new, one canonical per page.
  • Meta & social cards — per-page title/description, Open Graph + Twitter (cover as og:image), hreflang if multi-language.
  • Structured data — JSON-LD ComicSeries / Book, AggregateRating, BreadcrumbList, ItemList for feeds.
  • Sitemap & robots — chunked sitemap index for a large catalog; robots.txt; submit to Search Console + Bing.
  • Core Web Vitals — LCP (priority cover, preconnect, image CDN), CLS (reserve image dimensions), INP; a Lighthouse budget enforced in CI.
Exit series pages are indexed with rich previews; sitemap live; CWV in the green.

7

Production hardening & reliability

Engineering next-up
~3–5 wks

What separates "works on my machine" from "runs for real users" — the top engineering blocker to operating a public service, buildable in parallel with the legal call above.

  • ✓ Data durability — Litestream continuous backup (WAL → S3/B2, ~seconds RPO) + auto restore-on-boot; SQLite now in WAL mode. Opt-in via LITESTREAM_* env; runs plain without it. (Right-sized: single low-resource node; Postgres only if we ever run multiple server instances.)
  • Auth completeness — email verification + password reset (we have argon2 + sessions + rate limiting; verify/reset don't exist yet). Now the top remaining hardening item.
  • Observability — error tracking (Sentry), metrics + dashboards, alerting + on-call. Don't run public blind.
  • Secrets · TLS · host — managed secrets (B2 keys, admin, DB), TLS/domain, a real target (Fly.io / Railway / VPS).
  • Already done: security response headers, auth rate limiting, CI pipeline (fmt/clippy/build/check), Dockerfiles + compose stack, Playwright e2e scaffold, PRODUCTION.md tracker.
Exit durable data + backups, real accounts, eyes-on observability, secrets/TLS on a real host.

Beta & launch

~2–4 wks + ongoing

Ship carefully, watch closely, iterate.

  • Closed → open beta — feedback loop, bug triage, staged rollout.
  • Desktop release — code signing + notarization (macOS), installers (Win/Linux), Tauri auto-update.
  • Mobile — Tauri iOS/Android (tauri ios/android init + Android SDK/NDK; iOS toolchain present). The primary target now. App stores reject piracy readers (high legal risk), so plan for direct APK / sideload / TestFlight alongside any store attempt.

Exit public launch with monitoring, a rollback path, and a feedback loop running.
02

Production-readiness checklist

The cross-cutting surface for Phase 6 — the things that are invisible until they're missing.

Security

  • Web security headers — CSP, HSTS, X-Frame-Options, Referrer-Policy
  • Auth hardening + rate limiting + brute-force protection
  • Input validation & output encoding (OWASP Top 10)
  • Dependency + secret scanning; secrets manager
  • Pre-launch pen-test / security review

Observability

  • Structured logging with request correlation
  • Metrics + dashboards (Prometheus / Grafana)
  • Error tracking (Sentry) + tracing
  • Uptime monitoring + alerting + on-call

Performance

  • CDN + edge caching; image CDN (WebP/AVIF)
  • Bundle budgets; code splitting; lazy media
  • DB indexing, connection pooling, query review
  • Redis cache for hot reads; load testing

Reliability

  • Postgres backups + point-in-time recovery
  • B2 lifecycle; health checks; graceful degradation
  • DR runbook; defined SLOs; Suwayomi redundancy

CI / CD & QA

  • Pipeline: lint, typecheck, build, deploy
  • Tests — unit, integration, Playwright e2e
  • Preview deploys; staged rollout; IaC
  • Lighthouse / CWV budget gate

Donations & analytics

  • Donation flow — one-time + optional recurring, receipts
  • A processor that tolerates the content category
  • No paywalls / no feature gating — support is voluntary
  • Privacy-first analytics (Plausible / Umami) + consent

Legal & compliance

  • Terms, Privacy Policy, DMCA agent + takedown flow
  • GDPR / CCPA; cookie consent; data export/delete
  • Age gating for NSFW sources; content policy

Infrastructure

  • Web: Cloudflare Pages (SPA) + edge functions (SSR)
  • Server + Suwayomi + Postgres + Redis (Fly.io / Railway / VPS)
  • Domains, TLS, WAF, DDoS protection
  • Staging environment at prod parity

Open decisions

The calls that unblock the plan. Each one is yours to make — I've noted the lean.

✓ Decided · Backend stack for the unified serverRust — Axum + async-graphql + SQLite. Chosen for the smallest process footprint and to share the Tauri core's language; the unified server is built and verified on it. (SQLite now; revisit Postgres if multi-instance scale demands it.)
SSR for SEO — yes or no?Adopting edge SSR for public pages partially reverses "no SSR anywhere." Lean: yes, scoped to anonymous catalog routes — without it, organic discovery is severely capped.
✓ Decided · MonetizationDonations only — voluntary "keep it running" support. No paywalls, no feature gating, no ads. Softens the legal posture (non-commercial, community-funded); still needs a donation processor that tolerates the content category.
Distribution & legal postureStill open: aggregator (public + indexed) vs. self-host distribution vs. licensed/original content; web + desktop + PWA vs. app stores. Drives the DMCA/takedown, hosting, and store work.
Hosting & ops budgetCloudflare + a managed host (Fly.io/Railway) vs. a self-managed VPS. Lean: managed to start; revisit at scale.
