# N4.1 — Interpreter-only (Zero) OpenJDK for iOS arm64: findings (UNCOMMITTED)

> **Milestone.** N4.1 of `docs/plans/n4-ios-spike.md` §3 / §5 pre-gate: obtain or build an
> interpreter-only (Zero, NO-JIT — legal on iOS) OpenJDK runtime for **iOS arm64** capable of
> hosting the stock Suwayomi-Server jar (`v2.3.2243`) in-process via JNI.
> **Scope of this doc:** the runtime artifact + the reproducible recipe + honest blockers.
> On-device in-process boot is **N4.2** and is explicitly *not* provable here.
> **Env:** macOS arm64, Xcode 26.6 (iPhoneOS SDK 26.5), Homebrew JDK 21, ~228 GB free.

---

## 1. Decision: BUILD from source, not fetch

**No clean, general-purpose prebuilt iOS-arm64 Zero `libjvm` exists to download.** Researched:

| Candidate | What it actually ships | Usable as our in-process host JVM? |
|---|---|---|
| **OpenJDK Mobile Project** (`openjdk/mobile`) | Source only. README documents building a Zero `libjvm.a` static image for iOS. No binary releases. | **Yes — but must be built.** This is the path. |
| **Gluon "Java on Mobile"** (`download2.gluonhq.com/mobile`) | GraalVM-AOT / Substrate builds (`graalvm-…-darwin-gluon-*.zip`) + a `vmone.git` JVM lib, all oriented at **AOT-compiling one fixed JavaFX app**. | **No.** GraalVM-AOT compiles a specific app ahead-of-time; it does **not** boot an arbitrary stock jar (`JNI_CreateJavaVM` + classpath) in interpreter mode. Wrong technology for hosting `Suwayomi-Server.jar`. Their libffi+cups **support zip** *is* reused (below). |
| **PojavLauncher / Amethyst iOS** | Full OpenJDK for Minecraft, but relies on **JIT** via jailbreak / debugger / JIT-enabler. | **No.** Not interpreter-only; violates the no-JIT constraint that binds every Komika channel (§5/Q5). |
| **Maven Central `com.gluonhq`** | JavaFX SDKs / jmods, not a hostable iOS Zero `libjvm`. | **No.** |

Gluon's InfoQ-announced "automated build pipelines" (2025) automate *building* OpenJDK-mobile,
they do not publish a reusable general Zero `libjvm` artifact. **Conclusion: approach #2 (build).**
No `fetch-ios-jvm.sh` is written because there is nothing license-clean and general to fetch;
the reproducible builder is `scripts/build-ios-jvm.sh`.

**License:** OpenJDK is **GPLv2 + Classpath/Assembly Exception** (`LICENSE` = GPL2, plus
`ASSEMBLY_EXCEPTION` permitting static/dynamic linking of the OpenJDK code into a combined work).
This is the linking permission N4.2 needs to statically link `libjvm.a` into the iOS app binary.
Compatible with Komika's posture (the whole project is AGPL-3.0; GPLv2+CE linking is the intended
use). Never committed to git — built/vendored under `jre-ios/` (see §5).

## 2. The recipe (reproducible) — `scripts/build-ios-jvm.sh`

Derived from the `openjdk/mobile` README ("Build static image for iOS") and validated in this
environment through **configure success** (see §3). Pins:

- **Source:** `openjdk/mobile` @ commit `feb2de9b27dee5315d67448b4959beaaa77006a2` (JDK **28**-dev,
  verified 2026-07-16). This commit has the iOS `static-libs-image` target (JDK-8346233).
- **iOS libffi + cups:** Gluon `mobile-support-20250106.zip`
  (`https://download2.gluonhq.com/mobile/mobile-support-20250106.zip`),
  SHA-256 `5793dd8700612fe0c5a1cbbfb280464167aea5944b3c01f32b340542976e9440`, 8.85 MB.
  Verified its `libffi.a` is genuinely `arm64` with `LC_VERSION_MIN_IPHONEOS` (iOS platform).
  Zero needs libffi because it has no template interpreter — it calls native code via FFI.
- **Boot JDK:** **must be JDK 26, 27, or 28** (feature N/N-1/N-2 of HEAD). Auto-fetch option in the
  script pulls **Temurin 26.0.1+8** macOS aarch64.
- **Toolchain:** clang/LLVM from Xcode 26.6; sysroot from `xcrun --sdk iphoneos --show-sdk-path`
  (iPhoneOS 26.5 here).

Configure (the exact line that succeeded):

```
bash configure \
  --disable-warnings-as-errors \
  --openjdk-target=aarch64-macos-ios \
  --with-boot-jdk=<JDK 26/27/28> \
  --with-libffi-include=<support>/libffi/include \
  --with-libffi-lib=<support>/libffi/libs \
  --with-cups-include=<support>/cups-2.3.6 \
  --with-sysroot=$(xcrun --sdk iphoneos --show-sdk-path)
```

Build: `make CONF=ios-aarch64-zero-release static-libs-image`
→ `build/ios-aarch64-zero-release/images/static-libs/lib/zero/libjvm.a` (+ sibling static JDK
libs `libjava.a`, `libnio.a`, `libnet.a`, `libzip.a`, …).

Note: `--with-jvm-variants=zero` is **redundant** — Zero is the default (and only valid) variant
for the `ios` target, precisely because iOS has no writeable+executable pages. configure's summary
confirmed `JVM variants: zero`.

## 3. How far the build got in THIS environment

Every step **up to and including a live cross-compile of the Zero `libjvm.a`** ran here. Timeboxed;
the deliverable is the recipe + honest status, not a shipped binary.

| Step | Result |
|---|---|
| Install `autoconf` (brew) | ✅ 2.73 |
| Fetch + verify Gluon iOS libffi/cups support zip | ✅ SHA-256 match; `libffi.a` confirmed arm64 iOS |
| Shallow-clone `openjdk/mobile` (931 MB) | ✅ |
| `configure` with **JDK 21** boot | ❌ **Rejected** — the precise, reproducible blocker (see below) |
| Fetch Temurin **JDK 26** boot | ✅ 26.0.1+8 |
| `configure` with JDK 26 boot | ✅ **Success** — `JVM variants: zero`, target `ios/aarch64`, Xcode 26.6 toolchain, "A new configuration has been successfully created" |
| `make … static-libs-image` | ❌ **Failed at the hotspot os/bsd layer** after building the full interim host JDK and compiling the Zero interpreter (`bytecodeInterpreter.cpp`, `Creating …/libjvm/objs/static/libjvm.a from 839 file(s)`). Precise error below. |

**The exact JDK-21 blocker (verbatim):**

```
configure: Potential Boot JDK found at /opt/homebrew/opt/openjdk@21 is incorrect JDK version
  (openjdk version "21.0.11" …); ignoring
configure: (Your Boot JDK version must be one of: 26 27 28)
configure: error: The path given by --with-boot-jdk does not contain a valid Boot JDK
```

→ **The task's assumed "boot JDK = JDK 21" does not work.** `openjdk/mobile` HEAD is JDK 28-dev, and
OpenJDK enforces boot JDK ∈ {N-2, N-1, N}. Fix: use a JDK 26/27/28 boot (the script fetches
Temurin 26). This unblocks configure but is *not* the only blocker (next).

**The `make` blocker (verbatim), and why it is not a one-liner:**

```
src/hotspot/os/bsd/os_bsd.cpp:114:12: fatal error: 'libproc.h' file not found
    #include <libproc.h>
make[3]: *** [.../hotspot/variant-zero/libjvm/objs/static/os_bsd.o] Error 1
make[2]: *** [hotspot-zero-static-libs] Error 2
make: *** [static-libs-image] Error 2
```

`os_bsd.cpp` includes `<libproc.h>` under a plain `#ifdef __APPLE__`. `libproc.h` ships in the
**macOS** SDK but **not** the iPhoneOS SDK (confirmed: present under `MacOSX.sdk/usr/include`, absent
from every `iPhoneOS.platform` SDK). And it is not a single header — grepping the hotspot BSD layer at
this commit shows macOS-only libproc APIs used with **no iOS guard anywhere** (`grep -r TARGET_OS_IPHONE
src/hotspot/os/bsd` → **0 hits**):

- `os_bsd.cpp:2747` `proc_pidinfo(my_pid, PROC_PIDLISTFDS, …)`
- `os_perf_bsd.cpp:323` `proc_pidpath(pid, …)`
- `memMapPrinter_macosx.cpp:352/356/357` `proc_pidinfo(pid, PROC_PIDREGIONPATHINFO, …)`

**Root cause:** HEAD (`feb2de9…`) is titled *"Automatic merge of jdk:master into master"*. The mobile
project auto-merges mainline OpenJDK, and mainline's `os/bsd` layer has drifted to macOS-only libproc
usage. The mobile project's **iOS-enabling patches lag this latest auto-merge** — so **the HEAD commit
is not a green iOS build point**, even though the README's build steps themselves are correct. Building
mainline HEAD of an auto-merging downstream is the wrong pin.

**The correct fix is NOT to hand-port `os_bsd.cpp` here** (that would be inventing an iOS port and would
cascade through every unguarded `__APPLE__`/libproc site). It is to **pin an earlier `openjdk/mobile`
commit where the iOS static-libs build was actually validated** (the README + the `mobile-support`
zip are dated 2025-01-06, when mobile HEAD was ~JDK 25-dev — a boot JDK of 24/25 would match that era),
or to carry the mobile project's iOS patch series on top. Identifying and validating that exact green
commit is the remaining, bounded N4.1 work — see §4.

## 4. Feasibility verdict (Xcode 26.6, this machine)

**A from-source iOS Zero build is FEASIBLE in this environment — the toolchain works — but the pinned
commit choice matters and mainline HEAD is not green.** Evidence: configure succeeds cleanly against
Xcode 26.6 / iOS SDK 26.5 (`JVM variants: zero`, target `ios/aarch64`); `make` then builds the entire
interim host JDK and compiles the Zero interpreter before failing on the `os/bsd` libproc drift. So
none of clang, the iPhoneOS sysroot, libffi, the Zero interpreter itself, or the class-library compile
is a wall. The gates, in order of who they block:

1. **Boot JDK version** — must be 26/27/28, not 21. *Solved; effort: minutes* (script fetches Temurin 26).
2. **Commit pin / iOS port drift (the real blocker).** `openjdk/mobile` HEAD auto-merges mainline and
   its `os/bsd` layer has regressed to macOS-only libproc APIs with no iOS guards; it does not build for
   iOS as-is. **Must pin an earlier validated iOS commit (≈2025-01 / JDK-25 era to match the README +
   support zip) or maintain an iOS patch series.** *Effort: ~0.5–1 day to bisect/validate the green
   commit; then ongoing low-grade maintenance because the downstream keeps auto-merging mainline.*
3. **Build time / disk** — full JDK cross-build (interim host JDK + Zero hotspot + static native libs).
   Tens of minutes CPU; ~1 GB checkout + several GB build tree. *One-time per bump, CI-automatable.*
4. **`autoconf` + the Gluon support zip** — trivial prerequisites, both scripted.

**Effort estimate to a vendored artifact:** ~1–1.5 engineer-days the first time — the new cost vs. the
spike's estimate is item 2 (finding a green commit / patch set), which the spike's R2 already flagged
("independent OpenJDK-mobile build/debug effort"). Still **recipe reuse, not a fork**, but budget the
commit-pinning + a small standing iOS-port patch as real, recurring work.

## 6. EXACT next step for N4.2 (in-process on-device boot)

The iOS in-process launch differs from desktop in one fundamental way: **static linking, not a
child `java` process.** Desktop `suwayomi.rs` spawns `jre/<slug>/bin/java -jar Suwayomi-Server.jar`.
iOS has no process spawning and no app-loaded `.dylib`; instead:

1. **Link `libjvm.a` + the static JDK libs into the app binary.** In `apps/reader/src-tauri` the iOS
   target's build script / Xcode `gen/apple` project links `jre-ios/aarch64-ios/lib/zero/libjvm.a`
   and the sibling `*.a` (libjava, libnio, libnet, libzip, libjimage, …) plus the vendored
   `libffi.a`. The `JNI_CreateJavaVM` symbol then resolves at link time (no `dlopen`).
2. **Rust JNI Invocation API on a dedicated native thread.** Declare `extern "C" JNI_CreateJavaVM`
   (or use the `jni` crate's invocation feature against the statically-linked symbol) and create the
   VM with options mirroring the spike's §5 gate:
   `-Djava.awt.headless=true`, `-Dko…kcefEnabled=false`, `-Xmx256m` (jetsam-safe, §2 Q1),
   `-Xss` tuned, `java.class.path` = the extracted `Suwayomi-Server.jar`, and
   `-Djava.home` / boot module path = the vendored `lib/modules` runtime.
3. **Point `java.home` at the bundled runtime.** The static libs need the class library; set the VM's
   `java.home` to the app-bundle copy of `jre-ios/aarch64-ios` so `modules`/`lib` resolve.
4. **Boot the jar on that thread**, then drive `POST /api/graphql { aboutServer { version } }` and a
   MangaDex `fetchSourceManga` + chapter-list (installing the MangaDex extension via GraphQL first,
   to exercise dex2jar on-device). Reuse `suwayomi.rs` supervisor/readiness semantics; bind loopback.
5. **Tie to iOS lifecycle** (`applicationWillResignActive`/`DidEnterBackground` → pause/checkpoint;
   foreground → resume), per N4.2.
6. **Measure** cold-start ms + peak RSS vs the device jetsam ceiling (that is N4.3's go/no-go).

The Rust core / `src-tauri/src/**` and the `gen/apple` project changes are **owned by a parallel
agent / N4.2** — this milestone deliberately does not touch them.

## 7. could_not_verify (honest)

- **On-device in-process boot is NOT proven here.** iOS static libs cannot run on the mac host and
  the jar cannot be booted in-process in this environment — that is device + JNI-link work (N4.2/N4.3).
- **Cold-start / per-request latency under Zero on iOS: unknown** (only a device measures it — OQ1).
- **Whether the produced `libjvm.a` links + boots the stock jar cleanly** is a link-time/runtime
  question deferred to N4.2; the artifact's *architecture* (arm64 iOS mach-o) is checkable here via
  `lipo -info` / `vtool -show-build`, and the builder does that check, but "hosts Suwayomi" is not.
- **No `libjvm.a` artifact was produced** in this environment: `make` built the interim JDK and
  compiled the Zero interpreter but then failed on the `os/bsd` libproc drift (§3). So `jre-ios/` holds
  only the tracked `.gitkeep` — there is no binary to arch-check yet. The `lipo`/`vtool` sanity check in
  the builder is wired and correct; it simply had no output to run against this session. Feasibility of
  the *toolchain* is proven; a *shippable artifact* needs the commit-pin fix in §4 item 2.
