## 1. Decision: BUILD from source, not fetch

**No clean, general-purpose prebuilt iOS-arm64 Zero `libjvm` exists to download.** Researched:

| Candidate | What it actually ships | Usable as our in-process host JVM? |
|---|---|---|
| **OpenJDK Mobile Project** (`openjdk/mobile`) | Source only. README documents building a Zero `libjvm.a` static image for iOS. No binary releases. | **Yes — but must be built.** This is the path. |
| **Gluon "Java on Mobile"** (`download2.gluonhq.com/mobile`) | GraalVM-AOT / Substrate builds (`graalvm-…-darwin-gluon-*.zip`) + a `vmone.git` JVM lib, all oriented at **AOT-compiling one fixed JavaFX app**. | **No.** GraalVM-AOT compiles a specific app ahead-of-time; it does **not** boot an arbitrary stock jar (`JNI_CreateJavaVM` + classpath) in interpreter mode. Wrong technology for hosting `Suwayomi-Server.jar`. Their libffi+cups **support zip** *is* reused (below). |
| **PojavLauncher / Amethyst iOS** | Full OpenJDK for Minecraft, but relies on **JIT** via jailbreak / debugger / JIT-enabler. | **No.** Not interpreter-only; violates the no-JIT constraint that binds every Komika channel (§5/Q5). |
| **Maven Central `com.gluonhq`** | JavaFX SDKs / jmods, not a hostable iOS Zero `libjvm`. | **No.** |

Gluon's InfoQ-announced "automated build pipelines" (2025) automate *building* OpenJDK-mobile,
they do not publish a reusable general Zero `libjvm` artifact. **Conclusion: approach #2 (build).**
No `fetch-ios-jvm.sh` is written because there is nothing license-clean and general to fetch;
the reproducible builder is `scripts/build-ios-jvm.sh`.

**License:** OpenJDK is **GPLv2 + Classpath/Assembly Exception** (`LICENSE` = GPL2, plus
`ASSEMBLY_EXCEPTION` permitting static/dynamic linking of the OpenJDK code into a combined work).
This is the linking permission N4.2 needs to statically link `libjvm.a` into the iOS app binary.
Compatible with Komika's posture (the whole project is AGPL-3.0; GPLv2+CE linking is the intended
use). Never committed to git — built/vendored under `jre-ios/` (see §5).

## 2. The recipe (reproducible) — `scripts/build-ios-jvm.sh`

Derived from the `openjdk/mobile` README ("Build static image for iOS") and **validated in this
environment through a complete successful build** (see §3–§4). Pins:

- **Source:** `openjdk/mobile` @ commit `7e8729ef9298b86f90ceb5fb67dcd8008b047820`
  (**JDK 27-dev**, 2026-03-16, Johan Vos, "8380088: IOS: jit_write_protect_np not allowed" —
  the mobile project's **last iOS-specific fix** before mainline drift broke the iOS build the
  next day; see §3a for the evidence trail). Has the iOS `static-libs-image` target (JDK-8346233).
- **Vendored patch (1):** `scripts/ios-jvm-8380150-javacallarguments.patch` — a **verbatim
  upstream cherry-pick** of mobile/jdk commit `3ad532135e47` (2026-03-19, Kim Barrett,
  "8380150: JavaCallArguments defined too late"): one-line removal of
  `#include "runtime/os.hpp"` from `os_cpu/bsd_zero/atomicAccess_bsd_zero.hpp`. Required
  because the fix landed on master two days *after* the libproc drift, so **no patch-free green
  commit exists** (§3a). Applied by the script after checkout; provenance is the same GPLv2+CE
  repo, unmodified.
- **iOS libffi + cups:** Gluon `mobile-support-20250106.zip`
  (`https://download2.gluonhq.com/mobile/mobile-support-20250106.zip`),
  SHA-256 `5793dd8700612fe0c5a1cbbfb280464167aea5944b3c01f32b340542976e9440`, 8.85 MB.
  Verified its `libffi.a` is genuinely `arm64` with `LC_VERSION_MIN_IPHONEOS` (iOS platform).
  Zero needs libffi because it has no template interpreter — it calls native code via FFI.
- **Boot JDK:** **must be JDK 25, 26, or 27** (the pinned tree is JDK 27:
  `DEFAULT_ACCEPTABLE_BOOT_VERSIONS="25 26 27"`). The script auto-fetches **Temurin 26.0.1+8**
  macOS aarch64 (SHA-256 pinned).
- **Linker JDK (jimage tooling only):** **Temurin 27 EA (`jdk-27+30-ea-beta`)** macOS aarch64
  (SHA-256 pinned) — runs `jmod`/`jlink` to produce the target `lib/modules`, because the ios
  config cannot build its own jlink (no dynamic-lib support: Apple ld rejects `-soname`) and a
  same-tree macOS build would require the Xcode Metal toolchain component. Same feature
  version (27) as the tree, so it parses the v71 classfiles. See §4a for the exact mechanism.
- **Toolchain:** clang/LLVM from Xcode 26.6; sysroot from `xcrun --sdk iphoneos --show-sdk-path`
  (iPhoneOS 26.5 here).

Configure (the exact line that succeeded):

```
bash configure \
  --disable-warnings-as-errors \
  --openjdk-target=aarch64-macos-ios \
  --with-boot-jdk=<JDK 26/27/28> \
  --with-libffi-include=<support>/libffi/include \
  --with-libffi-lib=<support>/libffi/libs \
  --with-cups-include=<support>/cups-2.3.6 \
  --with-sysroot=$(xcrun --sdk iphoneos --show-sdk-path)
```

Build: `make CONF=ios-aarch64-zero-release static-libs-image`
→ `build/ios-aarch64-zero-release/images/static-libs/lib/zero/libjvm.a` (+ sibling static JDK
libs `libjava.a`, `libnio.a`, `libnet.a`, `libzip.a`, …).

Note: `--with-jvm-variants=zero` is **redundant** — Zero is the default (and only valid) variant
for the `ios` target, precisely because iOS has no writeable+executable pages. configure's summary
confirmed `JVM variants: zero`.

**Root cause:** HEAD (`feb2de9…`) is titled *"Automatic merge of jdk:master into master"*. The mobile

mainline HEAD of an auto-merging downstream is the wrong pin.

cascade through every unguarded `__APPLE__`/libproc site). It is to **pin an earlier `openjdk/mobile`
commit where the iOS static-libs build was actually validated**, or to carry the mobile project's iOS
patch series on top. That pin hunt was executed on 2026-07-17 — next section.

## 4a. How `lib/modules` is produced (the ios config cannot jlink itself)

`make static-libs-image` compiles **all** module classes into the exploded image
(`build/<conf>/jdk/modules`, 203 MB) but never runs jlink; `make jdk-image` is unbuildable for
ios (dynamic-lib `-soname` failure, §3a). The script therefore runs the pinned **Temurin 27 EA
linker JDK**'s `jmod`+`jlink` directly:

1. `jmod create --class-path <exploded java.base> --target-platform ios-aarch64` — jlink
   requires java.base's `ModuleTarget` attribute for a cross-platform link; exploded modules
   lack it (normally injected at jmod-packaging). `ios-aarch64` is the exact value the real
   build would use (`spec.gmk` `OPENJDK_MODULE_TARGET_PLATFORM`).
2. `jlink -J--patch-module=java.base=<patch-dir> --module-path <jmods>:<exploded modules>
   --add-modules ALL-MODULE-PATH` with two files patched into the **running** jlink VM:
   - `jdk/internal/util/OperatingSystem.class` from the ios build — teaches mainline jlink the
     `ios` platform (mobile patch JDK-8374522; mainline 27 EA rejects it with
     `Error: unknown target platform ios-aarch64`);
   - `jdk/internal/misc/resources/release.txt` copied from the target — jlink refuses to link
     when its own java.base release string differs from the target's; patching the running
     side (not the image) keeps the produced image's release string truthful
     (`N/A-27-internal-adhoc.<user>.mobile-…`, `SOURCE=…7e8729ef9298+`).
   Verified: the produced jimage has 27,262 entries, honest `ios-aarch64` ModuleTarget, honest
   release.txt. `ModuleTarget` is not enforced at boot (no `targetPlatform` reads in
   `ModuleBootstrap`/`ModulePath`), so the image boots like any jdk-image product.

## 6. EXACT next step for N4.2 (in-process on-device boot)

The iOS in-process launch differs from desktop in one fundamental way: **static linking, not a
child `java` process.** Desktop `suwayomi.rs` spawns `jre/<slug>/bin/java -jar Suwayomi-Server.jar`.
iOS has no process spawning and no app-loaded `.dylib`; instead:

1. **Link `libjvm.a` + the static JDK libs into the app binary.** In `apps/reader/src-tauri` the iOS
   target's build script / Xcode `gen/apple` project links `jre-ios/aarch64-ios/lib/zero/libjvm.a`
   and the sibling `*.a` (libjava, libnio, libnet, libzip, libjimage, …) plus the vendored
   `libffi.a`. The `JNI_CreateJavaVM` symbol then resolves at link time (no `dlopen`).
2. **Rust JNI Invocation API on a dedicated native thread.** Declare `extern "C" JNI_CreateJavaVM`
   (or use the `jni` crate's invocation feature against the statically-linked symbol) and create the
   VM with options mirroring the spike's §5 gate:
   `-Djava.awt.headless=true`, `-Dko…kcefEnabled=false`, `-Xmx256m` (jetsam-safe, §2 Q1),
   `-Xss` tuned, `java.class.path` = the extracted `Suwayomi-Server.jar`, and
   `-Djava.home` / boot module path = the vendored `lib/modules` runtime.
3. **Point `java.home` at the bundled runtime.** The static libs need the class library; set the VM's
   `java.home` to the app-bundle copy of `jre-ios/aarch64-ios` so `modules`/`lib` resolve.
4. **Boot the jar on that thread**, then drive `POST /api/graphql { aboutServer { version } }` and a
   MangaDex `fetchSourceManga` + chapter-list (installing the MangaDex extension via GraphQL first,
   to exercise dex2jar on-device). Reuse `suwayomi.rs` supervisor/readiness semantics; bind loopback.
5. **Tie to iOS lifecycle** (`applicationWillResignActive`/`DidEnterBackground` → pause/checkpoint;
   foreground → resume), per N4.2.
6. **Measure** cold-start ms + peak RSS vs the device jetsam ceiling (that is N4.3's go/no-go).

The Rust core / `src-tauri/src/**` and the `gen/apple` project changes are **owned by a parallel
agent / N4.2** — this milestone deliberately does not touch them.

## 7. could_not_verify (honest)

- **On-device in-process boot is NOT proven here.** iOS static libs cannot run on the mac host and
  the jar cannot be booted in-process in this environment — that is device + JNI-link work (N4.2/N4.3).
- **Cold-start / per-request latency under Zero on iOS: unknown** (only a device measures it — OQ1).
- **Whether the produced `libjvm.a` links + boots the stock jar cleanly** is a link-time/runtime
  question deferred to N4.2. What IS verified here (2026-07-17): every `.a` is arm64 mach-o with
  `platform IOS minos 26.5` (`lipo` + `vtool -show-build` on extracted members), and the
  `lib/modules` jimage is well-formed (`jimage list`: 27,262 entries; spot-extracted classes and
  release.txt read back correctly). "Hosts Suwayomi" remains unproven until N4.2.
- **The `lib/modules` jimage was linked by a Temurin 27 EA `jlink`, not by the tree's own** (the
  ios config cannot build its jlink — §3a/§4a). Same feature version (27), honest ModuleTarget +
  release string, and jlink's own compatibility gate passed; but "identical to what
  `make jdk-image` would emit" is unverifiable by construction. Risk assessed low (jimage is a
  container format; the class bytes come from the pinned tree's own javac output).
- **The 2026-03-16 pin was chosen from commit-history evidence, not an upstream CI green mark**
  (the mobile project publishes no iOS CI status). Evidence quality: it is the maintainer's own
  iOS build fix, and this environment compiled the full static-libs image at it (+1 verbatim
  upstream patch).
